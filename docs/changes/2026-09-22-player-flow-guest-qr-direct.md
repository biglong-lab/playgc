> 狀態：🟢 完成、已 push（未部署，等業主口令）
> 範圍 commit：`61030538`..`HEAD`（main）

## 背景（業主原話）

1. 善用不用登入的權限，讓使用者可以快速不用註冊就可以玩
2. 遊戲結束，有需要紀錄，再引導使用者註冊，建立身份或者登入既有的身份
3. 掃描遊戲 QR，要直接進入遊戲，不是進入大廳又要找會迷路
4. 開始遊戲前跳出沒必要的頁面資訊，影響體驗動線，請做通盤優化
5. （追加）積分開關：有些遊戲完全不需要積分、加減分，跟分數有關都不需要

## 盤點結論（改前）

最壞動線（首次掃 QR、未登入、單人）12 步：
QR 介紹卡 → 登入牆（文案「需登入組隊」但單人也擋）→ 平台場域列表 → 選場域 →
場域首頁 → 登入框 → 大廳一閃自動回跳 → 遊戲載入 → 繼續/重開框 → GPS 權限（最多 8 秒）→ 第一關（可能疊 PWA 卡/推薦隊伍框/版本自動 reload）

| 需求 | 根因 |
|---|---|
| 免登入 | Firebase 匿名登入已啟用（本地 DB 286 位玩家 266 位是訪客），後端 `isAuthenticated` 也接受；但前端每個入口先擋登入牆 |
| 結束引導 | 結算頁無引導；訪客改 Google/LINE 登入會換 uid，舊紀錄變孤兒；`linkAnonymousToEmail` 寫好沒人呼叫 |
| QR 直達 | QR 內容 `/g/{slug}` 本身正確；迷路是登入牆把人丟回 `/`；`/g/` 不在 `/f/` 下且沒用 `game.field.code` → 落到 JIACHUN |
| 開局彈窗 | 7 個可移除/延後：登入牆、暱稱框、繼續框、GPS、推薦隊伍框、PWA 卡、版本自動 reload |

## 解決方案

### Phase 1｜免登入 + QR 直達
- 遊玩類頁面（遊戲/章節/組隊/競賽/QR 過場）才觸發「背景自動建立訪客身分」，一般頁不觸發
- 拿掉登入牆：GamePlay、Home 未登入踢回、Landing「開始冒險」
- `/g/:slug` 改過場頁：套遊戲所屬場域、確認身分後 replace 導向；桌機阻擋提前
- 訪客暱稱自動產生，單人不再彈暱稱框
- 後端：建場次加 IP 限流

### Phase 2｜開局減法
- 繼續框 → 直接接續 + 可反悔 toast
- GPS 只在 `locationLockEnabled` 遊戲要求
- 沉浸式頁面不跳全站彈窗（推薦隊伍/PWA 卡），版本更新延到離開遊戲頁
- 組隊大廳：開始鈕只給隊長、倒數 5→3 秒、去重複 toast、進遊戲補 `/f/` 前綴

### Phase 3｜結束引導保存
- 結算頁「保存這次紀錄」卡（不強迫）+ PWA 安裝卡移到這裡
- 帳號認領：後端簽發 30 分鐘 HMAC 認領憑證 → 登入正式帳號後帶憑證呼叫認領 API → 搬移訪客資料
- LINE 登入回到原頁

### Phase 4｜驗證
- Playwright 真瀏覽器 e2e：未登入掃 QR → 第一關 → 通關 → 保存 → 登入 → 紀錄在帳號下
- 組隊雙瀏覽器流程；認領 API 單元測試

### 附帶
- 競賽/接力進行中不跳進遊戲（待實測）
- 隊伍獎勵 `issuedToUserId` 為 null，玩家「我的獎勵」看不到
- AdminStaffQRCodes 重產短連結呼叫不存在的 API
- 計分開關（games 加欄位，只加不刪）

## 已定決策
- 付費遊戲：付款前仍要求正式帳號（購買綁 uid，訪客身分遺失＝錢白付）
- 已通關再掃 QR：直接開新局
- 認領憑證用 HMAC 簽章、不建表（零 schema 變動）

## 改後動線

| 情境 | 改前 | 改後 |
|---|---|---|
| 掃 QR・單人（未登入） | 最壞 12 步 | **掃完直接第一關**（背景自動訪客身分，0 次點擊） |
| 有進行中進度 | 整頁繼續框 → 選 → 二次確認 | 直接接續 + toast「已從第 N 關繼續〔重新開始〕」 |
| 已通關再掃 QR | 停在結算畫面 | 直接開新局 |
| 章節 / 組隊 / 競賽 | 介紹卡 → 登入繞路 → 大廳 | 直達章節列表 / 組隊大廳 / 賽事大廳 |
| 開局定位權限 | 每局都要（最多卡 8 秒） | 只有地點鎖遊戲才要 |
| 結束 | 無引導 | 結算頁「保存這次紀錄」→ 登入後自動認領 |

## 部署注意

- `games.scoring_enabled`：server 啟動時自動 `ADD COLUMN IF NOT EXISTS`，不需手動遷移（已記 runbooks/db-migration.md）
- 認領憑證金鑰由既有 `SESSION_SECRET` 衍生，不需新增環境變數
- 選填 `SESSION_CREATE_IP_MAX`（建立場次 per-IP 上限，預設 200 / 10 分鐘）；大型活動前也請到 Firebase Console 確認匿名註冊配額
- 生產 Firebase 需維持「匿名登入」啟用（目前已啟用：本地 DB 286 位玩家中 266 位訪客）

## 已知限制 / 後續

- 認領刻意不搬：聊天、答題 / 投票 / 射擊等遊戲中暫存紀錄、水彈對戰（獨立系統）；排行榜舊列仍顯示訪客暱稱
- 唯一鍵衝突（例如同一章節兩邊都有進度）保留正式帳號那筆，訪客那筆原地不動（不合併進度）
- 競賽 / 接力模式本身仍不完整（前端沒呼叫回報分數、交棒、結束賽事 API；房主不在參賽者內）— 另案
- 計分關閉時，射擊 / 搶答等「以得分為過關條件」的元件內部計分照常（屬玩法機制，不是積分）
- 流程分支 `score_above / score_below`、條件驗證 `has_points` 在不計分遊戲恆以 0 分判斷，編輯器尚未警示
