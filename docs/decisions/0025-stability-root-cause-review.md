# ADR-0025: 穩定性問題的結構性根因盤點

> ⚠️ 2026-08-06 更號：原誤用 0024 與既有「MQTT v1 裝置通訊契約」撞號，依編號永不重用原則改為 0025。

> 日期：2026-08-05　狀態：採用中　影響：開發流程 / 即時層架構 / 測試策略

## 背景

業主反饋：「為了穩定性修改了好一段時間…每次都改好幾次好久，但實際上根本沒有對症下藥。」

這個質疑是對的。本文用 git 與生產資料量化驗證，並找出為什麼「一直修卻一直壞」。

---

## 一、量化盤點（近 6 個月）

### 1.1 git 歷史被雜訊污染 82%

| 項目 | 數量 |
|------|------|
| 全部 commit | 7,162 |
| **`chore(auto)` 自動存檔雜訊** | **5,878（82%）** |
| 真實 commit | 1,284 |

**影響**：`git log` / `git blame` / `git bisect` 幾乎失效。要追「這個 bug 什麼時候進來的」時，
訊號被 5,878 筆雜訊蓋住。這直接拖慢每一次除錯。

### 1.2 bug 高度集中在同一子系統

175 個 `fix` commit 中：

| 檔案 | fix 次數 |
|------|---------|
| `server/routes/websocket.ts` | 12 |
| `client/src/pages/team-lobby/useTeamLobby.ts` | 9 |
| `client/src/hooks/use-team-websocket.ts` | 8 |
| `server/routes/teams.ts` | 6 |
| `PhotoTeamFlow.tsx` / `ChoiceVerifyRacePage.tsx` | 各 6 |
| `server/routes/team-lifecycle.ts` | 3 |
| **多人即時系統合計** | **38（占全部 fix 的 22%）** |

同一個子系統被修 38 次 = 每次都在打補丁，沒有處理根因。

### 1.3 測試不是「沒有」，而是「測不到」

| 項目 | 現況 |
|------|------|
| 測試檔 | 231 |
| 測試案例 | 3,343 |
| e2e | 25 |
| 覆蓋率門檻 | 80% |

熱點檔案都有對應測試檔（`team-lifecycle.ts` 除外，0 個），但 bug 照樣反覆發生。

## 二、三個結構性根因

### 根因 A：用「成員身分」表達「在線狀態」🔴

> **2026-08-05 修正**：本節原本寫成「狀態雙軌」，深入查證後發現描述不精確，
> 且據此推導出的對策（把狀態搬 Redis）成本被高估。真正的問題是**概念混淆**，
> 修法比原先評估的小得多，已於當日完成根治，見文末「根治紀錄」。

`auto_leave` 存在有正當理由：`reevaluateTeamVotes` 的投票分母用
`isNull(leftAt)` 算「現任成員」。斷線者一直留在分母裡 → 投票永遠達不到
門檻 → 遊戲卡死。系統為了解卡，就去改斷線者的**成員身分**。

動機合理，但用錯機制：

```
為了解決「投票卡住」→ 去改「成員身分」→ 玩家回來發現自己不在隊上
```

- 「在隊」是**持久身分**，只該由玩家主動離隊或被踢而改變
- 「在線」是**瞬時狀態**，斷線就是斷線，不該影響身分

兩者被混為一談，才是所有斷線類 bug 的共同源頭。

### 根因 A（原始描述）：狀態雙軌 🔴

同一份「誰在隊上」的事實，同時存在兩個地方：

```
記憶體：teamClients / clients / matchClients : Map   （進程內）
DB    ：team_members.leftAt                          （持久層）
```

兩者由不同程式碼路徑各自更新，沒有任何機制保證同步。

**實證**（2026-08-05）：`auto_leave` 寫 DB 但重連只更新記憶體 →
生產 279 次 auto_leave 中 **71 次（25%）該玩家事後仍有 WS 活動**，
`team_members` 有 **98.7%** 被標記離隊。症狀是「切背景回來被踢出隊伍、
隊友畫面不同步」——但根因是同一份事實有兩個版本。

這違反最基本的 **single source of truth** 原則。只要雙軌存在，
就會持續產生新的不一致 bug，修完一個還有下一個。

### 根因 B：`websocket.ts` 複雜度失控 🔴

**1,286 行**，超過專案自訂的 800 行紅線 60%。內含：連線管理、認證、
20+ 種訊息類型、房間管理、寬限計時器、廣播、MQTT 注入、心跳。

單檔承擔太多職責 → 每次修改都可能碰到不相關的邏輯 → 修 A 壞 B。
這解釋了為什麼它是 fix 次數第一名。

### 根因 C：測試策略對「跨層問題」是盲的 🟠

現有測試大量 `vi.mock("../db")`。今天那個 `auto_leave` bug 的本質是
**記憶體與 DB 不一致** —— 把 DB mock 掉之後，這類 bug **在結構上就測不出來**。

測試數字（3,343）漂亮，但對真正會出事的那一類問題沒有防護力。

## 三、為什麼「改很多次卻沒效」

```
症狀出現 → 找到觸發點 → 打補丁 → 症狀消失
                              ↓
                    雙軌狀態仍在 / 檔案更肥 / 測試仍 mock
                              ↓
                        下一個不一致 bug
```

每次修的都是**症狀的觸發點**，不是產生症狀的**結構**。

---

## 四、決定

依「先止血、再治本」排序，且**不在活動前做高風險重構**。

### 階段 1：止血（低風險，立即做）

| 項目 | 理由 |
|------|------|
| 停掉 `chore(auto)` 自動存檔 commit | 82% 雜訊讓除錯失效；這是最高 CP 值的一件事 |
| 每修一個 bug 必附**真實 DB 整合測試** | 防止同類復發（已在 revenue / team-rejoin 實行） |
| deploy 前擋 `rules-of-hooks` | 已完成，防整頁 crash |

### 階段 2：補防護網（中風險）

| 項目 | 理由 |
|------|------|
| 為 38 次 fix 熱點補跨層整合測試 | 針對真正會壞的地方，而非追求覆蓋率數字 |
| `team-lifecycle.ts` 補測試（目前 0） | 它管離隊/踢人，出錯直接影響玩家 |

### 階段 3：治本（高風險，**活動後再做**）

| 項目 | 理由 |
|------|------|
| 狀態單一事實來源 | 消除根因 A。ADR-0023 的 Phase D 亦需要此前提 |
| 拆解 `websocket.ts` | 消除根因 B |

⚠️ 階段 3 涉及所有多人元件，在上百人活動前執行風險過高
（2026-07-04 多人腦裂事故即是此區域）。

## 五、已知限制

- 本盤點只涵蓋近 6 個月。
- 「fix commit 次數」是根因的**代理指標**，不等於嚴重度；已用生產 error_logs 交叉驗證。
- 未取得外部框架（如 Colyseus）的狀態一致性設計文件佐證，
  故此處僅引用通用的 single source of truth 原則，不虛構外部案例。

## 根治紀錄（2026-08-05）

### 已完成：投票分母改用「在隊 ∩ 在線」

```
原本：分母 = 在隊成員        → 斷線者卡住投票 → 只好改他的成員身分
根治：分母 = 在隊成員 ∩ 在線 → 斷線者自然不計入 → 不必動成員身分
```

- `reevaluateTeamVotes` 新增 `isUserOnline` 參數（不傳則沿用舊行為，供漸進遷移）
- 三個呼叫點全部接上 `RouteContext.isUserStillConnected`
- **分子仍看「在隊」**：人在隊上票就算數，即使此刻斷線
- **分母下限 1**：全隊同時斷線時不讓 0/0 被判成達標、把遊戲自動推進下一關

**不需要 Redis、不需要拆 `websocket.ts`** —— 這是原先高估成本的部分。

測試 6 項（`team-vote-online-denominator.test.ts`），關鍵案例挑
「4 人隊、2 人斷線、1 人投票」——多數決門檻是 ceil(分母/2)，
只有這種組合才能區分新舊行為（3 人隊 2 人投票兩者都會達標，測不出差異）。
已實測還原改動會轉紅。

### 尚未處理

`auto_leave` 本身仍會寫 `leftAt`。但它已不再是「解投票卡住」的必要手段，
下一步可評估延長寬限期或改為純在線狀態標記。建議累積真實數據後再動。
